## 서론
명탐정 코난은 일본에서 방영한 순서대로 정주행하기 복잡합니다. 스토리상 중요한 편과 중요하지 않은 편이 나뉩니다. 그리고 한국에선 방영하지 않았다가 미공개 X파일로 푸는 등의 이유로 순서가 뒤죽박죽입니다. 마지막으로 일본은 `n화` 형식인데 한국은 `m기 l화` 형식입니다.

그래서 코난을 쉽게 정주행할 수 있게 도와주는 [명탐정 코난 정주행]()을 개발하기 시작했습니다. 그런데 한국판 제목은 Source of Truth가 티빙 더빙, 티빙 자막, 라프텔 더빙, 라프텔 자막 총 네 개입니다. 따라서 출력되는 제목을 결정하기 위한 규칙은

1. 티빙 더빙에 있는 에피소드면 티빙 더빙의 공식 제목을 씁니다.
2. 티빙 더빙에 없으면 티빙 자막,
3. 티빙 자막에 없으면 라프텔 더빙,
4. 라프텔 더빙에 없으면 라프텔 자막,
5. 라프텔 자막에도 없으면 해당 에피소드는 포함하지 않습니다.

입니다. 이 규칙을 적용할 데이터를 생성하면서 겪은 시행착오에 대해 정리했습니다.

---

## 본론
### Single Source of Truth를 선택한 이유
이 프로젝트에서 Single Source of Truth(SSoT)라 하면 아래처럼 하나의 JSON 객체에 모든 OTT 링크를 다 포함하는 것입니다. `jp`는 일본 방영 순서입니다.

```json
{
  "group": "Part1",
  "number": 1,
  "title": "제트 코스터 살인 사건",
  "jp": {
      "group": "episode",
      "number": 1
  },
  "tving-dub": "https://www.tving.com/contents/E004283252",
  "tving-sub": "https://www.tving.com/contents/E003847937",
  "laftel-dub": "https://laftel.net/player/16919/63024",
  "laftel-sub": "https://laftel.net/player/41278/58456"
}
```

SSoT 방식으로 데이터를 생성하면 앱은 제목 결정 규칙을 모른 채로 데이터를 가져다 쓰기만 하면 되기 때문에 구현이 간단해집니다. 그리고 새로운 에피소드가 공개됐을 때도 파일 하나에 JSON 객체 하나만 추가하면 되기 때문에 확장성도 더 좋습니다.

데이터는 AI가 생성합니다. 일본 방영 순서를 지켜야 해서 방영 날짜를 포함하는 일본판 데이터를 먼저 생성했습니다. 티빙, 라프텔에서 에피소드 목록을 불러오고 일본어 제목과 유사도 기준으로 매핑해서 한국판 데이터를 만들었습니다. 프롬프트를 수정해가며 몇 번의 시도를 했으나 결국 데이터를 제대로 완성하지 못했습니다.

### Single Source of Truth를 포기했더니
SSoT 방식으로 데이터를 생성하지 않으면 아래처럼 작성하게 됩니다.

```json
{
  "group": "5기 Part1",
  "number": 1,
  "title": "유령주택의진실(전편)",
  "jp": {
      "group": "episode",
      "number": 274
  },
  "link": "https://www.tving.com/contents/E001499533"
}
```

```json
{
  "group": "5기",
  "number": 1,
  "title": "유령  집의 진실 (전편)",
  "jp": {
      "group": "episode",
      "number": 274
    },
  "link": "https://www.tving.com/contents/E003965028"
}
```

SSoT 방식으로는 생성하지 못했던 데이터를 이 방식으로 금방 완성했습니다. 즉, AI는 이 방식을 더 잘 이해하는 것 같습니다.

### Single Source of Truth를 고집했다가 토큰 다 날려먹은 이유
정확한 원인은 모르지만 결과론적으로 분석해봤습니다. 

SSoT일 때는 일본판 제목과 네 개의 소스, 즉 티빙 더빙, 티빙 자막, 라프텔 더빙, 라프텔 자막 모두를 비교해야 합니다. 그런데 네 개의 소스 중 하나 이상은 없을 수도 있습니다. 마지막으로 존재하는 소스 중 우선순위에 따라 대표 제목을 결정해야 합니다.

한편 데이터를 네 개로 분리했을 때는 일본판 제목과 한 번에 하나의 소스, 예를 들면 티빙 더빙 제목만 비교하면 됩니다. 우선순위를 결정할 필요도 없습니다. 즉, AI 입장에서는 복잡한 SSoT 데이터보다는 간단한 여러 개의 데이터가 생성하기 더 쉬웠던 것으로 판단했습니다.

## 결론
AI 시대 이전이었다면 사람 입장에서 직관적이고 작성하기 쉽고 앱 코드도 더 짧은 SSoT 방식을 선택했을 겁니다. 하지만 AI 시대에는 AI가 코드를 생성하고 유지보수 및 확장하기 때문에 AI 입장에서 쉽게 다룰 수 있는 구조를 선택해야 했습니다.

좋은 설계의 기준이 어쩌면 사람이 편한 설계에서 AI가 편한 설계로 바뀌고 있는 것처럼 느껴지는 게 재밌어서 글을 작성했습니다.
